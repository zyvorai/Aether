Each layer is independently testable. The adapter trait ensures new runtimes can be added without modifying the engine. The Decision Engine and Migration Engine operate on abstract workload models, making them runtime-agnostic by design.

Core Components

Four pillars form the foundation of the Aether engine, each responsible for a distinct concern.

⚙

Decision Engine

Evaluates workload specifications against runtime capabilities using a weighted scoring model. Considers resource limits, isolation requirements, scaling needs, and hardware affinity to select the optimal runtime. Supports manual overrides and constraint annotations.

🔌

Runtime Adapters

Each adapter implements a common trait with deploy, stop, status, logs, and migrate operations. Adapters translate Aether's abstract workload model into runtime-specific API calls. New runtimes are added by implementing the trait -- zero changes to the engine.

🗃

State Management

Workload state is persisted to a local JSON store with file-level locking for concurrency safety. State tracks deployment metadata, runtime binding, health status, and migration history. Designed for single-node reliability with optional remote sync.

🚀

Migration Engine

Orchestrates cross-runtime migrations with three strategies: immediate, blue-green, and rolling. Handles state transfer, health validation, traffic switching, and automatic rollback. Every migration is logged with full audit trail for compliance.

The adapter pattern is the key architectural decision. It makes Aether infinitely extensible without ever touching the core engine.

Adapter Trait Interface

#[async_trait]
pub trait RuntimeAdapter: Send + Sync {
    async fn deploy(&self, spec: &WorkloadSpec) -> Result<DeployResult>;
    async fn stop(&self, name: &str) -> Result<()>;
    async fn status(&self, name: &str) -> Result<WorkloadStatus>;
    async fn logs(&self, name: &str, opts: &LogOptions) -> Result<String>;
    async fn migrate(&self, name: &str, target: RuntimeType) -> Result<MigrateResult>;
    fn runtime_type(&self) -> RuntimeType;
}

Security Architecture

Aether implements defense in depth with encryption, authentication, audit logging, and input validation at every layer.

🔐

AES-256-GCM Encryption

All secrets are encrypted at rest using AES-256-GCM with unique nonces. Key derivation uses Argon2id with configurable memory and iteration parameters.

🔑

API Authentication

The API server uses token-based authentication with configurable expiry. Tokens are validated on every request via middleware before reaching any handler.

📜

Audit Integrity

Every operation is logged to an append-only audit trail with HMAC-SHA256 chain integrity. Tampering with any entry invalidates the entire chain.

📁

File Permissions

State files, secret stores, and configuration are created with restrictive permissions (0600). Directory permissions are set to 0700 to prevent unauthorized access.

🛡

Input Validation

All user input is validated and sanitized before processing. Workload names, image references, and resource limits are checked against strict allowlists and bounds.

⚖

K8s Resource Safety

Kubernetes deployments enforce resource limits, security contexts, and network policies by default. Privileged containers are blocked unless explicitly allowed.

Security is not a feature -- it is a property of the architecture. Every layer assumes the layer above it may be compromised.

Integrate via the REST API

# Deploy a workload via the API

  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "web-app", "image": "nginx:latest", "runtime": "auto"}'

# Check migration status
curl http://localhost:5090/api/workloads/web-app/status \
  -H "Authorization: Bearer $TOKEN"
