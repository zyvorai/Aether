Immediate Strategy

The fastest migration path — stop the source, start the target, validate, and update state. Ideal for development and staging environments.

Migration Timeline

1

Stop Source Workload

Gracefully stop the workload on the current runtime. Connections are drained and the container or VM is halted.

2

Start Target Workload

Deploy the workload to the destination runtime using the same YAML spec with runtime-specific adaptations.

3

Validate Health

Run health checks with exponential backoff. If validation fails, automatic rollback restores the source.

4

Update State

Persist the new runtime assignment to Aether's state file. The migration is now complete.

Use Cases

🛠

Development Environments

Fast iteration when testing workloads across different runtimes. Brief downtime is acceptable.

🏃

Staging Migrations

Validate runtime compatibility before production. Quick feedback loop on migration feasibility.

🕑

Maintenance Windows

Scheduled migrations during planned downtime. Simplest strategy with minimal resource overhead.

⚡

Stateless Services

Services that can tolerate brief interruption without data loss or session impact.

Command Example

# Migrate a workload from its current runtime to Kubernetes using the immediate strategy

  [4/4] Updating state...

Blue-Green Strategy

Zero-downtime migration with full validation before traffic switch. The target workload runs alongside the source until health is confirmed.

Migration Timeline

1

Start Target Workload (Green)

Deploy the workload to the destination runtime while the source (Blue) continues serving traffic.

2

Validate Target Health

Run comprehensive health checks against the Green deployment. Exponential backoff ensures thorough validation.

3

Switch Traffic

Once Green passes all health checks, update routing to point to the new runtime. Zero-downtime cutover.

4

Stop Source (Blue)

Gracefully decommission the Blue deployment. State is updated to reflect the new runtime assignment.

Advantages

🟢

Zero Downtime

Traffic is only switched after the target is fully healthy. Users experience no interruption during migration.

🔎

Full Validation

The target workload is validated in a live environment before receiving production traffic.

🔄

Instant Rollback

If the Green deployment fails health checks, the Blue deployment is still running. No rollback delay.

📊

Comparison Testing

Both deployments run simultaneously, allowing side-by-side performance and behavior comparison.

Command Example

# Blue-green migration to KubeVirt with zero downtime
$ aether migrate my-app kubevirt --strategy blue-green

Migrating 'my-app' to kubevirt (strategy: blue-green)...
  [1/4] Deploying green instance on kubevirt...
  [2/4] Validating green health (attempt 1/5)...
  [3/4] Switching traffic to green...
  [4/4] Stopping blue instance on kubernetes...
Migration complete: my-app now running on kubevirt (zero downtime)

Rolling Strategy

Gradual replica migration with health checks at every step. Traffic shifts incrementally from source to target, minimizing blast radius.

Migration Timeline

1

Deploy Initial Canary (10%)

Start a small subset of replicas on the target runtime. Route 10% of traffic to validate basic functionality.

2

Health Check + Scale (25%)

If the canary passes health validation, increase the target allocation to 25%. Monitor error rates and latency.

3

Progressive Expansion (50% / 75%)

Continue scaling the target while reducing the source. Each step includes full health validation with exponential backoff.

4

Complete Migration (100%)

All traffic is now on the target runtime. Source replicas are decommissioned and state is updated.

Exponential Backoff Health Validation

Each health check attempt uses exponential backoff to avoid overwhelming the target runtime during startup:

Delay Formula:  delay = base * 2^attempt  (capped at 30 seconds)

Attempt 1:  1s  * 2^0  =  1s
Attempt 2:  1s  * 2^1  =  2s
Attempt 3:  1s  * 2^2  =  4s
Attempt 4:  1s  * 2^3  =  8s
Attempt 5:  1s  * 2^4  = 16s  (max 5 attempts by default)

Canary Configuration

# Rolling migration with custom canary steps
$ aether migrate my-app kubevirt --strategy rolling \
    --canary-steps 10,25,50,75,100 \
    --health-interval 5s \
    --health-retries 5

Migrating 'my-app' to kubevirt (strategy: rolling)...
  Step 1/5: 10% on kubevirt — health OK
  Step 2/5: 25% on kubevirt — health OK
  Step 3/5: 50% on kubevirt — health OK
  Step 4/5: 75% on kubevirt — health OK
  Step 5/5: 100% on kubevirt — health OK
Rolling migration complete: my-app fully on kubevirt

Analysis Factors

📈

Resource Usage

CPU, memory, and storage requirements determine whether the target runtime can handle the workload. High-resource workloads favor rolling migrations.

🔗

Network Dependencies

Services with complex networking (ingress, service mesh, DNS) benefit from blue-green to validate connectivity before switch.

💾

Persistence

Workloads with persistent volumes or stateful data require careful migration. Blue-green ensures data integrity before cutover.

🎮

GPU Requirements

GPU-bound workloads have limited scheduling options. Advice factors in GPU availability across target runtimes.

Safety Features

Every migration is protected by multiple safety layers — from automatic rollback to state snapshots and health validation.

🔄

Automatic Rollback

If health validation fails at any stage, Aether automatically restores the source workload from the pre-migration snapshot. No manual intervention required.

💓

Health Validation with Exponential Backoff

Health checks use the formula base * 2^attempt with a 30-second cap. This prevents overwhelming newly-started workloads while ensuring thorough validation.

📷

State Snapshots Before Migration

A complete state snapshot is taken before every migration. This includes workload configuration, runtime assignment, and deployment metadata for guaranteed recovery.

🚫

Same-Runtime Guard

Aether blocks migrations where source and target runtimes are identical. This prevents accidental re-deployments and ensures migrations are intentional runtime changes.
