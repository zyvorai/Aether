What is KubeVirt?

KubeVirt extends Kubernetes with virtualization capabilities, allowing VMs and containers to coexist in the same cluster under the same management plane.

🖥

VMs on Kubernetes

KubeVirt adds a VirtualMachine CRD to Kubernetes, letting you define, schedule, and manage VMs just like pods. The kubelet handles VM lifecycle through the virt-handler DaemonSet.

🔄

Unified Scheduling

VMs are scheduled by the Kubernetes scheduler alongside containers. Resource requests, node affinity, taints, and tolerations all work the same way for both workload types.

🔒

Full VM Isolation

Unlike containers, KubeVirt VMs provide full hardware-level isolation via KVM. Ideal for legacy applications, compliance-sensitive workloads, and multi-tenant environments.

🌐

Kubernetes Networking

VMs connect to the same CNI network as pods. Services, Ingress, and NetworkPolicies work transparently, enabling VMs and containers to communicate natively.

KubeVirt is the bridge between legacy VM workloads and modern Kubernetes infrastructure — and Aether makes deploying to it as simple as deploying a container.

How Aether Deploys VMs

Aether's KubeVirt adapter generates two CRDs from your workload spec: a DataVolume for the disk image and a VirtualMachine for the VM definition.

DataVolume (Disk Image)

apiVersion: cdi.kubevirt.io/v1beta1
kind: DataVolume
metadata:
  name: my-vm-disk
  namespace: default
  labels:
    app: my-vm
    managed-by: aether
spec:
  source:
    registry:
      url: "docker://quay.io/containerdisks/fedora:40"
  pvc:
    accessModes:
      - ReadWriteOnce
    resources:
      requests:
        storage: 20Gi

VirtualMachine CRD

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: my-vm
  namespace: default
  labels:
    app: my-vm
    managed-by: aether
spec:
  running: true
  template:
    spec:
      domain:
        cpu:
          cores: 4
        resources:
          requests:
            memory: 8Gi
        devices:
          disks:
            - name: rootdisk
              disk:
                bus: virtio
      volumes:
        - name: rootdisk
          dataVolume:
            name: my-vm-disk

GPU Passthrough

Aether maps GPU requirements from your workload spec directly to KubeVirt GPU device passthrough, enabling ML training and inference workloads inside VMs.

Workload Spec with GPU

apiVersion: aether/v1
kind: Workload
metadata:
  name: ml-training-vm
spec:
  requirements:
    cpu: "8"
    memory: 32Gi
    storage: 100Gi
    gpu:
      count: 2
      vendor: nvidia
  runtime:
    preferred: kubevirt
    allow: [kubevirt]
  build:
    context: .
    dockerfile: Dockerfile
    registry: registry.example.com

Migration & Monitoring

Migrate workloads from containers to VMs with a single command and monitor VMs using the same Aether interface.

Container to VM Migration

# Migrate a running container workload to a KubeVirt VM
$ aether migrate my-app kubevirt --strategy blue-green

Aether treats VMs as first-class workloads. The same status, logs, health, and migrate commands work identically whether the target is a container or a virtual machine.

VMs Meet Kubernetes

Deploy virtual machines with the same simplicity as containers. One spec, one command, full VM isolation.

Deploy Your First VM

# 1. Create a VM workload spec
$ cat workload.yaml
apiVersion: aether/v1
kind: Workload
metadata:
  name: legacy-app
spec:
  requirements:
    cpu: "4"
    memory: 8Gi
    storage: 50Gi
  runtime:
    preferred: kubevirt
    allow: [kubevirt]

    context: .
    dockerfile: Dockerfile
    registry: registry.example.com
