Defense in Depth

Encryption at Rest

All sensitive data is encrypted using AES-256-GCM — the same authenticated encryption standard used by cloud providers and financial institutions.

Encryption Flow

User Key
→
SHA-256 Hash
→
32-byte Key
→
Random Nonce
→
AES-256-GCM Encrypt
→
Base64 Output

How It Works

The user-provided encryption key is hashed with SHA-256 to produce a fixed 32-byte (256-bit) key. A cryptographically random 12-byte nonce is generated for each encryption operation. The AES-256-GCM cipher provides both confidentiality and authenticity — any tampering with the ciphertext is detected on decryption. The final output is base64-encoded for safe storage and transport.

Key Properties

Property Value Purpose
Algorithm AES-256-GCM Authenticated encryption with associated data
Key Derivation SHA-256 Deterministic 32-byte key from any-length input
Nonce Size 12 bytes (96 bits) Unique per encryption, cryptographically random
Auth Tag 16 bytes (128 bits) Tamper detection and integrity verification
Output Format Base64 (nonce + ciphertext) Safe for JSON, YAML, and environment variables 
# Encrypt a secret value
$ aether encrypt --key my-encryption-key --value "database-password-2024"

Encrypted: k8Jd2f...base64...Qx9a==

# Decrypt a value
$ aether decrypt --key my-encryption-key --value "k8Jd2f...base64...Qx9a=="

Decrypted: database-password-2024

API Authentication

Every API request is authenticated via Bearer token. CORS protection ensures only authorized origins can access the Aether control plane.

Authentication Flow

Client Request
→
CORS Middleware
→
Bearer Token Check
→
Route Handler

Middleware Stack

🔓

AETHER_API_KEY

Set via environment variable. Every request must include Authorization: Bearer <key>. Requests without a valid token receive 401 Unauthorized.

🌐

CORS Protection

Cross-Origin Resource Sharing headers restrict which domains can call the API. Prevents unauthorized browser-based access to the control plane.

📋

Request Logging

Every authenticated request is logged with timestamp, actor, method, and path. Failed authentication attempts are flagged in the audit trail.

🛡

Rate Limiting

Built-in protection against brute-force attacks. Excessive failed authentication attempts trigger temporary lockout.

Configuration

# Set the API key via environment variable
$ export AETHER_API_KEY="your-secure-api-key-here"

# Start the Aether server with authentication enabled
$ aether serve --port 5090

# Authenticated API request
$ curl -H "Authorization: Bearer your-secure-api-key-here" \
     http://localhost:5090/api/workloads

# Unauthenticated request — rejected
$ curl http://localhost:5090/api/workloads
401 Unauthorized: Missing or invalid API key
Security is not a feature you add later — it is a foundation you build on. Every Aether API endpoint is authenticated by default with no opt-out.

Audit Trail Integrity

Every action in Aether generates an immutable audit event with SHA-256 integrity hashes. Tamper detection is built into every log entry.

Audit Event Structure

{
  "timestamp": "2026-04-12T14:32:01.847Z",
  "actor": "admin@example.com",
  "action": "deploy",
  "target": "my-app",
  "runtime": "kubernetes",
  "result": "success",
  "details": { "replicas": 3, "image": "app:v2.1.0" },
  "integrity_hash": "sha256:a1b2c3d4e5f6...64-char-hex"
}

Integrity Verification

🔒

SHA-256 Per Event

Each audit event includes a SHA-256 hash computed over its content. Any modification to the event data invalidates the hash.

🔍

Tamper Detection

When reading audit logs, Aether recomputes and verifies each integrity hash. Tampered entries are flagged with a warning.

👤

Actor Tracking

Every event records the authenticated actor (API key identity) who performed the action. No anonymous operations.

📅

Access Logging

Read access to sensitive resources is also logged, providing a complete picture of who accessed what and when.

Audit Commands

# View recent audit events
$ aether audit --last 20

# Filter by action type
$ aether audit --filter deploy,migrate,delete

# Verify audit trail integrity
$ aether audit --verify

# Export audit trail for compliance
$ aether audit --export json --output audit-report.json

State Security

Aether protects its internal state with atomic writes, advisory file locking, and restrictive file permissions — preventing corruption and unauthorized access.

Protection Layers

⚡

Atomic Writes

State is written to a temporary file first, then renamed to the target path. This ensures the state file is never partially written — even during power loss or crash.

🔒

Advisory File Locking

Uses POSIX flock to prevent concurrent state modifications. Multiple Aether processes coordinate safely through kernel-level advisory locks.

🛡

File Permissions

Backup and snapshot files are created with 0o600 permissions (owner read/write only). No group or world access to sensitive state data.

Atomic Write Flow

Serialize State
→
Write to .tmp File
→
fsync()
→
rename() to Target

Why Atomic Writes Matter

The POSIX rename() syscall is atomic on all major filesystems. By writing to a temporary file first and then renaming, Aether guarantees that the state file is always in a consistent state. If the process crashes during the write, the temporary file is simply orphaned — the original state file remains intact.

File Permission Model

File Type Permission Octal Access
State file rw------- 0o600 Owner read/write only
Backup files rw------- 0o600 Owner read/write only
Snapshot files rw------- 0o600 Owner read/write only
Audit log rw------- 0o600 Owner read/write only
Config directory rwx------ 0o700 Owner full access only

Kubernetes Resource Safety

Production-grade Kubernetes interactions with timeouts, conflict resolution, cleanup guarantees, and strict input validation.

⏰

5-Minute Timeouts

All Kubernetes API operations have a 5-minute timeout. No operation can hang indefinitely — if the API is unresponsive, the operation fails cleanly with a descriptive error.

⚠

409 Conflict Handling

When a resource update conflicts (HTTP 409), Aether automatically retries with the latest resource version. Optimistic concurrency control prevents lost updates.

🗑

Resource Cleanup on Failure

If a deployment fails mid-way, Aether cleans up partially-created resources. No orphaned Deployments, Services, or ConfigMaps left behind.

📌

Namespace Validation

Target namespaces are validated before deployment. If the namespace does not exist, Aether creates it with appropriate labels rather than failing silently.

DNS-1123 Input Validation

All resource names, namespace names, and labels are validated against the DNS-1123 standard before any Kubernetes API call is made:

  • Must be lowercase alphanumeric characters or hyphens
  • Must start with an alphanumeric character
  • Must end with an alphanumeric character
  • Maximum 63 characters for labels, 253 for hostnames
# Invalid name caught before API call
$ aether deploy My_App --runtime kubernetes

Validation error: 'My_App' is not a valid DNS-1123 name
  - Uppercase characters are not allowed
  - Underscores are not allowed (use hyphens instead)
Suggestion: use 'my-app' instead
